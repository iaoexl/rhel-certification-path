## README · 从 RHCSA 到 RHCE 的系统化学习路径

这是一套面向从零基础到生产运维的 Linux 系统知识体系，也是从 RHCSA（EX200）走到 RHCE（EX294）的一条完整路径。全库以红帽企业版技术体系为主线，按"认知—部署—命令—脚本—权限—存储—网络—服务—自动化—架构"的能力递进逻辑重组为二十三个板块，每个板块都可独立学习、独立验证、独立归档。板块内容不堆砌概念，而是解析技术背后的设计动机，理顺知识点之间的因果关系，再用可复现的操作与验证把原理落到手上。

板块顺序本身即一条可执行的备考路径：第 1 至 11 板块逐条落完 EX200 的十个模块，第 12 至 17 板块是考纲之外、岗位上必用的服务能力，第 18 板块承接 EX294 的自动化要求，第 19 至 22 板块走向网络存储与规模化交付。每个板块末段给出对应的考纲模块、闯关任务与自检问题，模块与板块的完整对照见 README_8。

全库统一遵循一条编写主线：先讲清"为什么需要它"，再讲透"它是怎么工作的"，最后给出"怎样做、怎样记、怎样验证"。命令以 `root@iaoexl:~#` 作为统一提示符，图示以 ASCII 代码块绘制，配置与输出以等宽代码块呈现，保证在任何阅读环境下都能完整显示。

### README_3 场景笔记方法：实验笔记的版本化管理

技术学习最大的隐性损耗不是"不会"，而是"当时会了，后来忘了"。解决办法是把每一次实验都沉淀为结构化、可检索、可回溯的笔记，并用版本控制工具把它管理起来。下面这套方法贯穿全库所有板块，各板块的"场景笔记方法"段落会给出针对该场景的具体模板。

笔记采用"三栏记录法"，每一条实验记录都包含三个部分：操作与命令（原样记录执行的命令或配置）、实际输出与现象（原样粘贴关键输出，或描述观察到的现象）、结论与疑问（用自己的话写下结论，并记录尚未理解的地方）。三栏缺一不可，因为命令保证可复现，输出保证可对照，结论保证内化。

```
实验笔记条目结构
┌──────────────────────────────────────────────┐
│ 场景：静态 IP 配置        日期：<当日填写>    │
├──────────────────────────────────────────────┤
│ 【操作】nmcli con mod ens160 ...              │
│ 【输出】connection successfully activated     │
│ 【结论】会话配置即刻生效，无需重启网络服务    │
│ 【疑问】多网卡时会话名如何区分？→ 待验证      │
└──────────────────────────────────────────────┘
```

笔记的版本化管理按"本地提交 + 多平台备份"的思路进行。本地用 Git 建立仓库，每个板块对应一个子目录，每次实验结束即提交一次，提交备注写清"板块编号 + 场景 + 动作"，例如"更新笔记：板块11 网络会话配置"。远程仓库可同时托管在多个代码托管平台，日常推送到各自的主分支，形成异地备份。

```
笔记归档流程
   编辑笔记 ──► 检查修改 ──► 本地提交 ──► 推送远程 ──► 异地备份完成
      │            │            │            │
   三栏记录     区分新增/修改   写清提交备注   GitHub/Gitee/GitCode
                 （红/蓝标识）               按需选择平台
```

图形化工具下的日常操作要点：提交前先用"检查修改"确认本次改动范围，新增文件与修改文件以不同颜色标识，核对后勾选本次要提交的文件；提交只写入本地仓库，不会自动上传；推送时选择对应远程源，本地分支与远程分支保持一致，日常推送不勾选强制类选项，以免覆盖他人改动；拉取用于把远程的最新改动同步回本地，形成闭环。首次推送需要先绑定上游，之后按常规流程推送即可。凭证由凭据管理器保存，使用个人访问令牌完成认证，避免在命令行明文暴露密码。

```
┌──────────┐   提交    ┌──────────┐   推送    ┌──────────────┐
│ 工作区笔记 │ ───────► │ 本地仓库  │ ───────► │ 远程仓库(多平台)│
│ 三栏条目  │ ◄─────── │ 版本历史  │ ◄─────── │ 异地备份      │
└──────────┘   检出    └──────────┘   拉取    └──────────────┘
```

### README_4 实用验证方法论

验证分三层，逐层收紧。第一层是命令级验证，确认单条命令的输出符合预期；第二层是配置级验证，确认配置文件改动被服务正确读取；第三层是场景级验证，从用户视角确认整个功能可用。只有三层全部通过，才算完成一次实验。

虚拟机环境是验证的安全垫。任何有破坏性的操作都应先在虚拟机中进行，并在关键节点保存快照；一旦配置失控，用快照在数秒内回滚到正常状态，再重新验证。这与在生产环境中反复重装相比，效率提升非常明显。

排错遵循"由外到内、由简到繁"的顺序：先确认网络连通与防火墙状态，再确认服务进程是否运行，接着确认配置文件语法与参数，最后查看日志定位细节。多数故障集中在前两步，按顺序排查可以避免在配置细节里盲目打转。

```
验证三层模型
  场景级验证 ── "用户能否真正用起来"   （如：浏览器能否访问网站）
       ▲
  配置级验证 ── "服务是否读取了新配置" （如：查看运行时生效参数）
       ▲
  命令级验证 ── "单条命令是否正确"     （如：systemctl status）
```

### README_5 能力自检与进阶节奏

每个板块末尾都设有能力自检问题，用于确认是否真正理解而不只是读懂。建议以"能否不看笔记复现实验""能否向他人讲清原理""能否在报错时独立定位"作为三道通关标准。三道都通过，方可视为真正掌握；若反复卡壳，应回到基础知识检查根基是否牢固。

学习节奏上，重操作类板块以动手为主，重原理类板块以图解为主，服务类板块以"部署—验证—破坏—恢复"的循环为主。把每个板块的笔记按统一模板归档，长期积累后即可形成一份可检索、可复用的个人技术手册。

EX294 还有一条前置要求写着"能分析简单的 Shell 脚本"——那是板块4 的功底，读不懂既有脚本就改不动它。走 **EX342（企业 Linux 排障）** 的，除板块5 的启动与救援外，还需关注板块7 的文件系统修复、板块8 的 LVM 恢复、板块10 的 SELinux 排错、板块18 的批量修复能力；kdump、AIDE、PAM、集中式日志这些专题在主干中只作点到，深入需要另配资料。

考纲对标的用法不止于"看表"。每个板块的"认证对标与进阶实战"段末都有一组闯关任务，只给目标不给命令，用来检验该板块对应的考点是否真能独立完成；正文里按场景分组的命令表格本身即可当速查表用，需要成体系记忆时按"认证对标"表回溯到具体板块。模拟练习则建议按考试节奏做：先限时完成单板块闯关，再跨板块组卷，最后在虚拟机上从裸系统开始复现整条链路。

版本语境必须写在前面：本库以 RHEL 9 与 RHEL 10 共用的命令体系为主线，差异单独标注。RHEL 10 的影响面集中在五处——包管理器实现（DNF 4 与 DNF 5 的差异）、AppStream 模块化内容不再分发（改用版本化包名）、RPM 数据库迁移到 `/usr/lib/sysimage/rpm`、ifcfg 网络配置彻底移除（仅 keyfile）、默认加密策略禁用 SHA-1。考场上以实际系统为准，凡与本库表述不一致处，以 `dnf --version`、`cat /etc/redhat-release`、`man` 的输出为最终依据。
